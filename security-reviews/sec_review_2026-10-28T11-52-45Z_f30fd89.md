## Findings

### Finding 1: Script injection via PR file names in `pull_request_target` workflow — `.github/workflows/sync-pr-labels.yml:140`

- Severity: High
- Confidence: 0.9
- Category: ci_script_injection (GitHub Actions "pwn request")
- Description: The "Sync PR Labels" workflow runs on `pull_request_target`, so it runs for fork PRs
  with the base repository's context, a `GITHUB_TOKEN` with `pull-requests: write` and
  `issues: write`, and access to repository secrets. Step "Get changed files" (line 114) writes the
  PR's changed file names, as returned by `pulls.listFiles`, to the step output `files` via
  `JSON.stringify`. Step "Apply file-based labels" then puts that output straight into the
  github-script source:
  `const changedFiles = JSON.parse('${{ steps.changed-files.outputs.files }}');`.
  `${{ }}` is replaced as text before the script is parsed, and `JSON.stringify` does not escape
  single quotes. A file name containing `'` therefore closes the JavaScript string literal, and
  whatever follows runs as code inside `actions/github-script` (which has `require`, an authenticated
  `github` Octokit client, and the runner environment). Git allows `'`, `(`, `)`, `+` and `;` in
  path names. `/` is not needed because the payload can build strings with `String.fromCharCode`.
  The job-level guard `github.repository_owner == 'AOSSIE-Org'` is true for PRs to the upstream
  repo, and `pull_request_target` runs need no maintainer approval.
- Exploit Scenario: An attacker forks the repo and opens a PR that adds a file whose name is shaped
  like `x'+(<JS expression>)+'.md`. The workflow renders
  `JSON.parse('["x'+(<JS expression>)+'.md"]')`, and the expression runs while the argument is
  evaluated. With that code execution the attacker can at least:
  (a) use the job's `GITHUB_TOKEN` to label, comment on, close or edit any issue or PR, and submit PR
  reviews (approvals also count if the repo lets Actions approve PRs);
  (b) tamper with the runner, for example by rewriting the cached `actions/github-script` bundle under
  the runner's `_actions` directory, so that the later "Apply contributor-based labels" step
  (line 262) leaks `secrets.EXTERNAL_LABELLER_TOKEN`, a separate, likely broader token that is also
  used by `coderabbit-approval.yml`;
  (c) use the Actions cache runtime token, which JavaScript actions receive, to write cache entries in
  the default-branch scope. Those entries could poison the `.next/cache` restore (with its
  `restore-keys` prefix fallback) or the npm cache that `nextjs.yml` uses when it builds and deploys
  the production GitHub Pages site. Path (c) depends on cache-key prediction or eviction and is
  conditional; (a) follows directly from the code.
- Recommendation: Never put step outputs or event data into `script:` or `run:` with `${{ }}`.
  Either compute the file list in the same github-script step that applies labels (drop the
  `changed-files` output), or pass it through an environment variable:
  `env: { CHANGED_FILES: ${{ steps.changed-files.outputs.files }} }` and
  `const changedFiles = JSON.parse(process.env.CHANGED_FILES);`. Also move the
  `EXTERNAL_LABELLER_TOKEN` step into a separate job, so code running in one job cannot reach the
  other job's secret. Use `pulls.listFiles` with pagination (`github.paginate`) if all files are
  needed.

## Limitations

**Standing limitations**

- This review does not replace a full manual audit or a penetration test.
- This is static analysis of source text. Nothing was executed, fuzzed, or traced at runtime, so
  timing-dependent, load-dependent, or infrastructure-dependent issues cannot be confirmed here.
- Confidence scores are the reviewing model's own self-assessment, not a calibrated statistical
  probability.
- Absence of a reported finding does not mean the code is secure. Safety guardrails built into some
  models can cause a real vulnerability to be softened, generalized, or left out rather than
  reported in exploit-level detail, and training-data bias can make some vulnerability classes
  easier for a model to recognize than others. Treat this report as a floor on what a full audit
  would find, not a ceiling.
- Findings reflect the reviewing model's training data cutoff. A vulnerability tied to a very
  recently disclosed CVE or library advisory may not be recognized as such.

**Review-specific limitations**

- Finding 1: the injection payload is described in shape only (`x'+(<JS expression>)+'.md`), not as
  a working exploit string. The code-execution primitive is fully supported by the source.
  Escalation paths (b) and (c) depend on runner and cache behaviour that cannot be verified
  statically.
- Repository settings were not available: secret scopes, whether `EXTERNAL_LABELLER_TOKEN` is set
  and what scopes it has, whether "Allow GitHub Actions to create and approve pull requests" is
  enabled, branch protection, and Pages environment protection rules. These settings change how far
  Finding 1 can reach.
- Third-party actions referenced by tag instead of SHA (`eps1lon/actions-label-merge-conflict@v3`,
  `release-drafter/release-drafter@v6`, `AndreasAugustin/actions-template-sync@v2`,
  `actions/github-script@v7`) were not reviewed at source. Dependency contents under `node_modules/`
  and `package-lock.json` were out of scope.
